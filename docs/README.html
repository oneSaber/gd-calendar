广东地下演出日历（GD Live Calendar）

聚合 广东地区（广州 / 深圳 / 佛山 / 东莞 / 珠海 / 中山 / 惠州 / 汕头） 的 地下偶像（地偶）、女子乐队、ACG 乐队 演出信息， 生成可筛选、可订阅的演出日历。

垂类定位：本项目的静态站只保留垂类内容（地偶 / 女子乐队 / ACG）—— 普通摇滚演出、脱口秀、话剧等不进入线上日历。判定口径见 SPEC.md 的「发布口径」。

全自动采集 → 中文文案解析 → 实体归一化 → PostgreSQL/SQLite → REST + .ics → 日历界面。

快速开始

一键启动（推荐）

双击 启动.bat 即可。它会自动完成：

检查 Python → 按需创建 .venv 并装依赖 → 生成 .env → 建库
→ 启动服务 → 轮询直到真正可用 → 打开浏览器

首次会问两件事（可直接回车接受默认）：

  1. 缺依赖时是否创建 .venv 并安装（只影响项目目录，不动系统 Python）
  2. 库里没数据时是否采集一轮（约 1–3 分钟）

命令行传参：

启动.bat                            :: 默认 127.0.0.1:8000
启动.bat -Port 8010                 :: 换端口
启动.bat -Fetch                     :: 强制采集一轮（用配置里的全部城市）
启动.bat -Fetch -City 广州,深圳       :: 只采指定城市（会覆盖默认的 8 城）
启动.bat -Fetch -Sources showstart,douban,bilibili,weibo   :: 含浏览器源（需 Edge/Chrome）
启动.bat -NoBrowser                 :: 不自动开浏览器
启动.bat -AutoInstall               :: 缺依赖时不再询问
停止.bat                            :: 停止服务（会核对命令行，不会误杀其它程序）
⚠️ -City / --cities 会覆盖默认城市列表（默认 8 城全部启用：广州 深圳 佛山 东莞 珠海 中山 惠州 汕头）。想采全部就别传这个参数——我自己踩过：一直传 广州,深圳， 结果珠海等 6 个城市一场都没采到，还以为是抓漏。 改城市列表请改 .env 里的 ENABLED_CITIES。

功能开关

页面上的两个入口可以通过 .env 统一控制（改完重启服务）：

FEATURE_ICS=false        # 「＋ 订阅这个日历」与「加进我的日历 (.ics)」
FEATURE_UPDATE=false     # 「↻ 更新数据」按钮

前端 app/web/js/features.js 里有一份静态兜底值，保证后端不可用（或 GitHub Pages 上没有后端）时开关依然生效。改那个文件可以直接控制页面行为，刷新即可。

注意：关掉的只是页面入口，POST /api/admin/update 接口与 更新数据.bat 照常可用 —— 定时任务不该被 UI 开关影响。

只读静态站点（GitHub Pages）

本项目是动态应用（FastAPI + SQLite + 浏览器采集器），而 GitHub Pages 只能托管 静态文件。所以有一个导出器，把数据落成 JSON 让前端离线工作：

python -m app.cli build-static          # 输出到 docs/（Pages 的发布目录）
python -m app.cli build-static --out site
python -m app.cli build-static --no-occurrences   # 只出计数，体积更小

只发布垂类内容：地偶 / 女子乐队 / ACG。判定是「或」关系（任一标记命中即保留）， 与界面上多选标记的「与」语义不同——「与」是用户主动收窄，这里是站点范围。 同时会过滤场地列表、页脚统计与月历计数，保证四处口径一致 （有测试锁住：点阵合计 == 明细条数）。

发布口径：与 ACG 有关 + 满足任一演出条件

不能只凭标题像演出就发布。 规则是或关系：

大前提：这条内容与 ACG 有关（is_idol / is_girl_band / is_acg 任一为真）
小前提（满足任一即发布）：
  a) 演出阵容里有地偶 / ACG 乐队 / 女子乐队  ← 最可靠
  b) 活动主题与日本 ACG 音乐或偶像有关（品牌白名单）
  c) 命中已核实的具体厂牌/企划名

为什么 (a) 最可靠：秀动的列表页只在真有演出人员时才给阵容。 实测对照：

规则 (b) 的白名单（_MUSIC_IDOL_FRANCHISES，27 种写法）只放日本音乐/偶像 向的品牌：BanG Dream! / 哭泣少女乐队 / 孤独摇滚 / 轻音少女 / 偶像大师 / LoveLive! / 赛马娘 / 少女歌剧 / D4DJ / Project SEKAI。 不放游戏与少年漫（明日方舟 / 型月 / 卡拉彼丘 / 全职猎人 / 第五人格 / 阴阳师 / 高达 / 重返未来1999 / 特摄）——它们的 only 展是普通漫展。 实测这区分是必要的：库里 16 条「同人/only」只有 2 条属于音乐/偶像向。

阵容里的名字要先过知识库：_looks_like_performer() 会先查演员知识库， 命中已知团体就算演出人员（哪怕名字里拼了「-1018生诞祭版」这类应援物后缀）； 没命中且带商品字样（应援/周边/特典/版本号）才当非演出人员剔除。

同一原则也用在标题分类器：classify(title, extra, lineup=...) 接受阵容， 阵容含已知垂类团体时可以压过展会/应援/情报类噪音判据。 实测「koyo生诞祭应援」标题含「应援」会被当噪音，但阵容里是地偶团体 DigitalDuel —— 确实是演出，应当保留。

分类：先看演出人员，再看标题

标题只能说明「谁办的」，演出人员才说明「谁演的」。 所以：

  1. 演员知识库（app/normalize/artist_kb.py）——人工/联网核实过的团体名，

每条带 evidence（来源 URL）与 confidence

  1. 命名规则兜底（偶像/女子乐队/ACG/乐队）
  2. 阵容投票：命中某类的演员数即为票数
  3. 与标题判定取并集（标题会误报，阵容会漏报——阵容缺失率约 32%）

为什么必须有知识库：「恋时青空」「比邻星球企划」「月匙Moon-Key」这些真地偶团体 的名字里一个地偶关键词都没有，靠标题永远认不出来。

陌生名字不猜：进 unknown 列表，留给联网核实或人工 review。 artist.kind 用 unknown 表示「还没核实」，只有带 evidence 的条目才进知识库 ——否则每个陌生演员都会被当成"已知"，投票就失去意义。

python -m app.cli artist-kb              # 同步种子知识库到 artist 表
python -m app.cli reclassify --dry-run   # 按阵容重算分类（先看会改多少）
python -m app.cli reclassify --report    # 实际执行并打印明细

重分类的每处改动都会写进 review_task 并附依据（阵容、票数、前后标记） ——这是推断而非事实，必须可复核、可回滚。

只更新数据（不启服务）

双击 更新数据.bat。适合放进 Windows 计划任务做定时更新。

更新数据.bat                                                  :: 默认 HTTP 源，约 1–3 分钟
更新数据.bat -Sources showstart,douban,bilibili,weibo -UseBrowser

更新数据.bat -Backfill                                        :: 顺手重算分类标记
更新数据.bat -DryRun                                          :: 只看会做什么，不改动

它会自动选模式：

情况行为
服务在运行调 /api/admin/update 任务接口，终端显示实时进度；页面上的更新按钮也会同步看到同一任务
服务没运行直接跑 python -m app.cli fetch

两种模式都会先跑一次数据库结构迁移。

⚠️ 采集后必须按顺序做后处理（用 refresh）

这一步很容易漏，也很容易把顺序搞错 —— 实测踩过：先 reclassify（按阵容） 再 backfill（按标题）会把阵容得到的结论清掉，事件就从日历里消失了 （「koyo生诞祭应援」就是这样掉出去又恢复的）。

所以用这条组合命令，它把正确顺序固定下来：

python -m app.cli refresh                # 采集 + 后处理 + 重建静态站（全流程）
python -m app.cli refresh --no-fetch     # 跳过采集，只做后处理 + 重建
python -m app.cli refresh --skip-static  # 不重建静态站

依次执行：采集 → artist-kb → reclassify → backfill → build-static， 任一步失败立即中止并返回错误码。

顺序为什么不能变：

步骤依赖
artist-kb必须最先 —— reclassify 要先把知识库同步进 artist 表
reclassify按阵容判定（最可靠），应在 backfill 之前
backfill只按标题判定；已改成与现有标记取并集（不再清掉阵容结论）
build-static必须最后 —— 否则导出的是旧标记

页面上的「更新数据」按钮

顶栏右上角。点击后：

↻ 更新数据  →  ↻ 32%   ← 按钮变忙、显示百分比
────────────────────────────────
秀动：采集中…（0/2） 已用 32 秒     ← 进度条 + 实时消息，可展开看详细日志

设计要点（都是踩过坑才这么做的）：

  • 不是同步请求：一轮采集 1–3 分钟，同步 HTTP 必然超时，也拿不到进度。

所以后端做成进程内任务（app/jobs/update_job.py），前端启动 + 轮询。

  • 单任务并发保护：同一时刻只允许一个采集任务。按钮点两下、

或脚本与页面同时触发，第二次都复用既有任务而不是再起一个 （SQLite 单写者，并发采集只会互相锁）。 早期实现靠「遍历找 state=='running'」判断，在「任务已创建但协程还没开始跑」 的窗口里会漏判，现在用显式的 _running_id。

  • 未定进度动画 + 已用秒数：单个来源要跑 1–2 分钟，进度百分比长时间不动。

只显示 0% 会让人以为卡死，所以切到流动条纹并在消息里显示「已用 N 秒」。

  • 完成后自动刷新列表、月历、场地下拉与页脚统计，并清掉月历计数缓存。
  • 刷新页面会通过 GET /api/admin/update 恢复进行中的任务状态，不会丢进度。

脚本编码约定（改脚本前务必看）： scripts/*.ps1 必须是 UTF-8 with BOM，否则 PowerShell 5.1 会按 GBK 解析、中文变乱码； *.bat 必须是纯 ASCII，因为 cmd.exe 按 ANSI/GBK 解码 .bat，中文注释会被当成命令执行。 中文界面文案一律由 PowerShell 侧输出。

像地王广场（广州商场中庭）这类免费场地，演出不上售票平台， 秀动/豆瓣/B站都拿不到。实测线索：

需要与「偶像」「公演」组合用

  • 微博上有聚合速览贴（如「本周广州偶活速览」）——一次覆盖整周免费/小型场次，

  • 漫展里的地偶舞台（如东莞萤火虫）用「漫展 + 偶像 + 舞台」类关键词覆盖

小红书（垂直特定：需要维护者自己的登录态）

小红书所有页面都要求登录（搜索页正文是「登录后查看搜索结果」）， 所以要采集必须借助登录态。做法与 scripts/xhs_publish.py（发布助手）同一条路：

  • 用持久化 profile（%LOCALAPPDATA%\gd-calendar\xhs-profile），扫码一次可长期复用
  • 走平台自己的 UI 页面，只读公开可见内容
  • 不注入 Cookie、不伪造签名、不逆向私有接口、不改指纹
小红书登录.bat          :: 起可见浏览器，扫码
小红书采集.bat          :: 按内置关键词采集（需先登录）
python -m app.cli xhs status                       # 看登录态
python -m app.cli xhs collect                      # 按内置词表采集
python -m app.cli xhs collect --keywords "广州地偶"  # 指定关键词

结果落 data/xhs_notes.json（标题 + 作者 + 链接），不直接进库 —— 笔记正文里才有演出时间/地点/阵容，需要人工或后续解析确认。

微博关键词表怎么定

每个关键词 ≈33 秒（渲染移动端搜索页 + 拦截 XHR），词表要精挑，不能盲目扩表：

python scripts/probe_weibo_keywords.py     # 实测候选词的产出量

实测对标后定下 16 个词，覆盖四类：聚合速览 / 各地偶 / 免费场地 / ACG 同人。 理由见 app/collectors/weibo.py 的 SEARCH_KEYWORDS 注释。

微博解析质量（已修 / 待改进）

微博正文是自由文本，解析噪音比秀动/豆瓣多。实测发现并已修掉：

问题表现修法
「…全文」截断标记被当场地库里出现 ...全文、活动舞台 ...全文clean_venue 剥离截断标记 + 清理 7 条垃圾场地
短碎片被当场地凝固、活短名必须含场地特征词，否则判噪音
日期被补到明年「9日」已过 → 2027-06-07距博文发出 >120 天丢弃 + 清理 4 条荒谬场次

仍存在的：抽奖/福利贴可能被当活动（正文有日期字样但没有真实场次）。 需要继续用 looks_like_event 类判据收紧。

数据质量护栏（都是实测踩过的坑）：场地名里混入的地址会被剥离（否则同一场地每周重复插入）、 纯日期串不会被当成场地、主催情报 这类公告不会被当成活动、阵容字段里的 / 会拆成多个团体、 非演出内容（脱口秀/话剧）默认不出现在日历里。

分类标记：地偶 / 女子乐队 / ACG

三个互相正交的标记，可以叠加（一个 ACG 女子乐队三个都为真）：

标记字段判定要点
地偶is_idol地偶信号多于乐队信号；也是主分类（决定卡片色条与日历点色）
女子乐队is_girl_band全女子编制；女子偶像属于地偶，不算女子乐队
ACGis_acg动画/漫画/游戏/二次元/同人/宅向

关键词是收紧过的——泛词会制造假阳性，实测被教育过两次：

曾经的写法误判结果
痛（单字）「澈心之痛2026深圳专场」被判成 ACG
op主题曲「东方古典与北美爵士的巧妙融合一《弦·无界》」被判成 ACG
女声摇滚同上一场被判成女子乐队（「女声」只说明主唱性别）

现在只保留明确说法（痛车/痛包、动画主题曲、全女子/女子乐队/ガールズバンド）。 这两条反例都写进了 tests/test_flags.py，防止以后又放宽。

筛选支持两种写法，语义都是「与」：

GET /api/occurrences?flag=女子乐队&flag=acg     # 同时命中两者
GET /api/occurrences?is_girl_band=true&is_acg=true
GET /api/calendar/counts?month=2026-10&city=广州 # days[].girl_band / days[].acg
GET /api/ics?is_idol=true&is_acg=true           # 日历名会变成「ACG地偶演出日历」

界面上是两个独立的可点按钮（✓女子乐队 ✓ACG），与「全部类型/乐队/★地偶」正交叠加； 日历格子里用 女 / A 角标表示当天含该类场次。

标记只增不减：同一活动有多个来源时，某个源标题信息更少（没写「ACG」）， 不会把别的源已判定出的标记抹掉。

数据库结构升级

Base.metadata.create_all 只建缺失的表，不会给已有表加列。所以：

python -m app.cli initdb      # 建表 + 自动补齐缺失的列（幂等，推荐）
python -m app.cli migrate     # 只做结构迁移
python -m app.cli backfill    # 按当前分类器重算历史数据的分类标记
python -m app.cli backfill --dry-run   # 先看会改多少，不落库

服务启动时也会自动跑一次迁移（app/db/migrate.py），所以升级不会丢已采集的数据。

新增标记后必须跑一次 backfill：否则存量活动不会带上新标记， 用户会看到「筛女子乐队一条都没有」。 自动迁移目前只支持 SQLite；PostgreSQL 请用 Alembic。

场地名保留城市前缀：珠海乐坊、深圳B10现场、广州CH8蛙厂演艺中心(大学城店) 都保留城市， 只有在城市后面确实跟地址时才剥（广州市越秀区北京路纵一咖啡 → 越秀区北京路纵一咖啡）。 早先无条件剥城市前缀，把 深圳B10现场 切成了 B10现场 —— 既丢信息， 又会让不同城市的同名场地混淆。

采集覆盖范围：默认覆盖广东省 8 个城市（广州 深圳 佛山 东莞 珠海 中山 惠州 汕头）。 珠海/东莞/佛山等城市主要由秀动城市页 + 豆瓣同城覆盖（当地没有自营排期站）。

实测一次全 8 城 HTTP 采集（约 160 秒）：
  广州 145 · 深圳 120 · 珠海 36 · 东莞 25 · 佛山 15 · 惠州 10 · 中山 2 · 汕头 2

为什么微博要拦截 XHR 而不是直接调 API：m.weibo.cn 的个人主页会强制跳登录， 直接请求 api/container 返回 432；唯一可行路径是让页面自己去请求，我们抄它的 JSON。 这不是绕过鉴权——不注入 Cookie、不伪造签名、不破解验证码。

核心设计取舍

1. event 与 occurrence 分离

地偶「定期公演」按月重复、乐队「巡演」多站、同一系列有「第 1 期 / 第 2 期」， 所以日历的最小单位是 occurrence，event 只承载稳定身份（标题/系列/分类）。

2. 三层判重，绝不静默合并

层依据行为
1source_code + external_id直接更新（幂等）
2指纹（场地+日期+标题+阵容）命中即合并，挂多来源
3同城同日同场地 + 标题相似度 ≥ 0.65合并 + 记 review_task
—相似度不足保留两条（同一天下午场+夜场是真实存在的）

冲突（两个来源给出不同时间）不静默覆盖，写入 review_task 并在前端并列展示。

3. 场地是最大的语义坑

  • MAO 广州有 4 个店（六元素 / 永庆坊 / 太古仓 / 中大），不是 2 个。
  • 「太空间 Livehouse」与「MAO 太古仓店」是两个场地，地址门牌相邻（太古仓码头 5 号仓 vs 4 号仓）。

→ 硬规则：门牌/仓位号不同即不同场地；「太古仓」禁止作为任何场地的别名。

  • 源里的场地名常带完整地址（豆瓣：「场地名 + 街道号」）→ 入库前必须剥离，

否则同一场地会被反复插成新纪录。

4. 数值类型按真实数据选

字段类型原因
priceNUMERIC(8,2)存在 ¥0.01 占位票、¥9.90
series_volTEXT存在 Vol.13 / Vol33.0 / 第一期 / ①
age_limitTEXT广东普遍用身高（「1.2m 以下儿童谢绝入场」）而非年龄
标题存 3 份title_raw（原样，含 emoji/Unicode 粗体）/ title_display（排版）/ title_norm（去重）

5. 时间统一带 +08:00 输出

SQLite 不保存时区：写进去的 aware datetime 读出来是 naive。 若直接序列化，前端 new Date("2026-11-01T20:00:00") 会按浏览器本地时区解析， 在非东八区整体偏 8 小时。因此 API 层对所有时间字段强制补 +08:00。

中文文案解析器（app/parsers/text_zh.py）

这是项目真正的技术护城河：把微博博文、场地动态、票务页脚注这类自由文本抽成结构化场次。

覆盖的实测形态：

时间  「时间：2026年8月29日16:00」「📅 2026.09.24 🕖 19:00 入场」
      「11月7日 周六 19:30 开演，19:00 开场」「OPEN 18:30 / START 19:30」
价格  「¥180起」「¥9.90起」「预售80 现场100」「无料入场」「普通票 ¥0.01」
      「¥237 VIP / ¥457 VIP+」（VIP 是票种名不是标签）
场地  「[广州]游声场FreeField」「地点：广州天河」「📍广州市越秀区…（2F）」
阵容  「参演团队：@A @B @C」「出演：A / B / C」「A × B × C」
分类  乐队 / 地偶（生诞·定期公演·Oneman·联合）/ 排除脱口秀话剧

解析过程中修掉的真实 bug（都有对应测试）：

  1. 日期 2026年8月29日16:00 里的数字被当成票价（8 / 29 / 16）。
  2. OPEN 18:30 / START 19:30 里 OPEN 抢占开演时间 → 引入「已认领时间要屏蔽」+「紧邻才认」。
  3. ¥237 VIP 里 VIP 被当成 237 的标签 → 拆成三段式扫描（币种 / 引导词 / 元·起）。
  4. 入场：48.8 1D 里的 1D（票种代号）被当成 ¥1。
  5. 太古仓 4 号仓 与 5 号仓 被误合并。
  6. MAO Livehouse广州中大店 里的「馆」被当地址特征 → 场地名被截成 MAO。
  7. 我的 emoji 字符类误伤全角 ＋；clean_text 顺序必须先 emoji 后半角。

两条必须守住的口径不变式

这两个都踩过坑，且都有回归测试锁住（tests/test_store_and_api.py）：

  1. 日历点阵与列表必须同口径。 /api/occurrences 默认 exclude_other=True

（过滤掉 kind='other' 的脱口秀/展览/旅游等非演出内容）， /api/calendar/counts 必须接受同一个参数。 早期 counts 没有这个参数 → 日历显示圆点、点进去空白。 > 不变式：某天 counts.band + counts.idol == 该天列表的 total。

  1. 过期判断按「天」，不按「时刻」。 豆瓣很多活动只给日期、没有时刻，统一存当天

00:00 且 date_precision='date_only'。若用 start_at >= now - 6h 过滤， 这类当天的活动会在当天下午就被隐藏。 > 不变式：当天 00:00 的 date_only 场次，当天任何时刻都可见。

.ics 要点：UID:{occurrence.id}@gdcalendar 稳定不变，改期时更新 DTSTART 并递增 SEQUENCE，日历客户端会更新而不是重复添加。

海报为什么必须走后端代理

实测结论：豆瓣图片有防盗链 —— 浏览器/客户端直接请求 https://img3.doubanio.com/... 返回 HTTP 418，带上 Referer: https://www.douban.com/ 才返回 200。所以前端 <img src="原站地址"> 一定裂图。

因此海报一律经 /api/archive/poster?url=...：

浏览器 ──▶ /api/archive/poster?url=...  ──▶ 按域名补 Referer ──▶ 原站图床
                     │
                     └─ 按内容 sha256 缓存到 data/posters/（二次请求 X-Poster-Cache: hit）

配套的三个防护：

  1. 域名白名单（doubanio.com / hdslb.com / showstart.com），非白名单返回 403 ——

否则这个接口会退化成任意 URL 的开放代理（SSRF 风险）。

  1. 协议白名单：只接受 http/https，javascript: data: 一律丢弃。
  2. 前端失败降级：海报加载失败时 error 事件（捕获阶段）就地替换成

「首字 + 渐变」占位，不显示浏览器裂图图标。

海报覆盖率（实测）：295 个活动中 68 个有海报（23%）。

来源活动数带海报说明
豆瓣4342RSS/列表页直接带图
B站2624cover 字段（需补 https:，是协议相对 URL）
微博42部分博文带图
秀动2250见下

秀动为什么没有海报

三处都实测过：

  1. 列表页条目的海报是懒加载的，SSR HTML 里只有 <div class="image-slot"> 占位

（全页出现的 img04.showstart.com 全是 JS/CSS 资源，没有一张演出海报）；

  1. 详情页 /event/{id} 也是 SPA 壳（实测仅 ~19KB，没有 og:image）；
  2. 前端 XHR /api/web/activity/list 直接调用被 WAF 拒

（GET → get_not_support「方法受限」；POST → 参数不全）。

→ 结论：秀动海报只能靠浏览器渲染详情页获取（225 场 × 渲染成本，尚未实现）。 app/cli.py fetch --posters 保留了这条路径的探针，但它会明确报告实测无效， 不会假装成功——宁可不显示海报，也不灌脏数据或做签名逆向。

如果你需要秀动的海报，可行做法是给「按需补图」加一个浏览器渲染的懒加载路径 （用户点开某场详情时再抓那一张），而不是全量预抓 225 场。

合规边界

  1. 不绕过任何鉴权：不破解验证码、不注入登录 Cookie、不逆向签名

（秀动 App 的 crpsign、大麦的 mtop、B 站的 wbi 一律不做）。 需要浏览器的地方只做「渲染 + 读页面自己请求到的数据」。

  1. 遵守 robots：mp.weixin.qq.com、weixin.sogou.com、m.weibo.cn、xiaohongshu.com

实测均为 Disallow: / → 不做批量抓取（搜狗微信路线直接排除）。

  1. 限速：单域名 ≥ 1 req/3s；豆瓣按其 Crawl-delay: 5 执行；浏览器源 12h 一次。
  2. 只存事实：标题/时间/场地/票价作为事实数据；不整篇转载文案、不搬运海报原图，

详情页标注来源并回链。

  1. 不采集个人信息：博文里的 @ 仅用于阵容匹配，不入个人库。
  2. 收到通知即下线。
判例背景：「实质性替代」是核心裁判逻辑（汉涛诉百度案二审判赔 323 万元）。 抓「时间/场地/乐队/票价」这类事实字段 + 显著回链导流，与「抓 UGC 全文替代原平台」 性质不同，风险显著更低，但仍需自律。
